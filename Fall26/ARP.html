ARP Behavior on a VirtualBox NAT Network

A short lab walkthrough for capturing and reading ARP traffic between two VMs (SEEDA, SEEDB) on the same NAT Network, and identifying what 10.0.2.3 actually is.

arp -n Wireshark NAT Network 10.0.2.0/24 2 VMs
1

Start both VMs and run arp -n

Boot both seedA and seedB and open a terminal on each. Run the ARP cache lookup on both machines side by side:

$ arp -n

Both VMs should show 10.0.2.1 as a known neighbor on enp0s3 — this is the NAT Network gateway. Note each VM's own IP in the shell prompt (SEEDB is 10.0.2.15, SEEDA is 10.0.2.29 here).

2

Start Wireshark on SEEDB and filter by ARP

On SEEDB (either VM works), launch Wireshark from the taskbar or Applications menu.

  1. On the Wireshark welcome screen, select the enp0s3 interface — this is the NAT Network adapter carrying traffic between the VMs and the gateway.
  2. Double-click it (or press the blue shark-fin ▶ button) to start a live capture.
  3. Let it run for a minute or two while both VMs are idle-but-connected — this gives ARP time to fire naturally.
  4. In the display filter bar at the top, type arp and press Enter to narrow the packet list down to ARP requests/replies only.
3

Filter the packets using MAC address and protocol

To isolate just the broadcast ARP requests (the "who has X?" queries, as opposed to the unicast "is at" replies), combine the ARP protocol filter with a MAC address condition targeting the broadcast address ff:ff:ff:ff:ff:ff:

arp && eth.dst == ff:ff:ff:ff:ff:ff

This filters on two things at once: the protocol (arp) and the destination MAC address field (eth.dst) — showing only the broadcast "who has …?" requests, since replies are always sent as unicast directly to the requester's real MAC.

4

Examine the ARP packet

Click any ARP packet in the list and expand it in the detail pane below. Key fields to look at:

  • Opcode — 1 for a request ("who has"), 2 for a reply ("is at").
  • Sender MAC / Sender IP — who's asking (or answering).
  • Target MAC / Target IP — in a request, the target MAC field is all zeros, since that's exactly what's being asked for.

In the filtered list above, note the repeating pattern:

  • PcsCompu_13:92:85 → Broadcast: "Who has 10.0.2.3? Tell 10.0.2.15" — seedB asking for the MAC of 10.0.2.3.
  • PcsCompu_8e:51:5b → Broadcast: "Who has 10.0.2.15? Tell 10.0.2.3" / "Who has 10.0.2.29? Tell 10.0.2.3" — 10.0.2.3 itself asking for the MACs of both VMs.

This two-way questioning is a strong signal that 10.0.2.3 is an active host on the segment that is itself initiating traffic toward the VMs — consistent with it being a service (like a DNS resolver) that needs to talk back to whichever VM queried it.

Reflection Questions

Q1. Why do ARP packets keep getting re-initiated?

Looking at the timestamps in the filtered capture, the same "who has 10.0.2.1?" or "who has 10.0.2.3?" query repeats every few minutes even though the answer never changes.

Answer

Each host keeps a local ARP cache mapping IP → MAC addresses, but entries in that cache expire after a timeout (on Linux this is typically around 60 seconds to a few minutes, tunable via the kernel's neighbor table settings). Once an entry ages out, the next time that IP needs to be reached, the OS has to issue a fresh broadcast ARP request to relearn the MAC address — even if nothing on the network actually changed.

Additional reasons ARP traffic recurs:

  • Continued traffic to that IP after the cache entry has expired (keep-alive re-resolution).
  • A host restarting its network stack or renewing a DHCP lease, which flushes its cache.
  • Periodic housekeeping — some systems proactively re-verify neighbor reachability at intervals.

This is exactly why the capture shows the same "who has 10.0.2.1 / 10.0.2.3 / 10.0.2.15?" exchanges repeating in a loop rather than happening just once.

Q2. What is 10.0.2.3?

10.0.2.3 is the virtual DNS name server provided by VirtualBox's NAT engine — not a second gateway.

Answer

Per Oracle's own VirtualBox documentation (User Manual, §9.6.1 — Fine Tuning the NAT Engine), when a VM is attached in NAT mode with only one NAT instance active, the addressing is fixed by convention:

  • 10.0.2.15 — the guest VM's IP
  • 10.0.2.2 (or 10.0.2.1 on a NAT Network, as used here) — the gateway
  • 10.0.2.3 — the name server (DNS)

Source: Oracle VirtualBox User Guide, Release 7.2

This lines up with what the ARP capture shows: both VMs periodically ask "who has 10.0.2.3?" right before sending DNS lookups, and 10.0.2.3 answers back and also asks for the VMs' MAC addresses in return — because the virtual DNS proxy needs to know where to route its responses.
